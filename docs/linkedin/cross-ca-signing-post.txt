Cross-CA signing: one key, two roots, and why it keeps the internet from breaking. 🔐

Recent conversations around CA trust in India put a critical PKI mechanism back in focus: cross-certification.

When a CA's own root isn't trusted everywhere yet — a new root, a migration, or a trust change at the browser/OS level — cross-signing is what keeps certificates working in the meantime.

So it's worth understanding properly. 👇


🔸 What it is

Normally the trust path is simple:
Root → Intermediate → leaf.

Cross-signing gives the SAME intermediate CA key pair — same subject, same public key, ONE private key in the HSM — TWO certificates from TWO independent roots:

→ the CA's own root
→ a second, already widely trusted root

The private key never changes. Only an extra certificate is bound to it.

Result: one leaf certificate now chains to EITHER root. Clients that trust only the second root still trust your leaf.


🔸 When it's used

→ A new root not yet in browser/OS trust stores — cross-sign under an established root so you're trusted from day one.
→ Root rollover / migration — old and new roots both validate during the transition.


🔸 How it's generated (a demo I built)

Two independent roots: eMudhraDemo and SectigoDemo.

1️⃣ Generate the intermediate key pair INSIDE the HSM, create one CSR.
2️⃣ eMudhraDemo Root signs the CSR → cert A (native chain).
3️⃣ SectigoDemo Root signs the SAME CSR → cert B (the cross certificate). Same subject, same public key, different issuer.
4️⃣ The intermediate signs ONE leaf (CN=www.demo.example).

Verified with OpenSSL:

✅ leaf → intermediate (cert A) → eMudhraDemo Root
✅ leaf → intermediate (cert B) → SectigoDemo Root

Same leaf. Same intermediate key. Two trust anchors.


🔸 Binding it to the HSM

The cross certificate is bound to the EXISTING private key — you do NOT generate a new key.

In the HSM you end up with one private key object and two certificate objects sharing the same CKA_ID.

→ Java: keyStore.setKeyEntry(alias, existingHsmKey, null, chain)
→ pkcs11-tool: --write-object ... --id <same-id-as-the-key>

The CKA_ID match IS the binding.


⚠️ What to watch out for

→ Same subject DN + same public key across both certs — otherwise it isn't a cross cert.
→ The leaf is bound to the KEY, not to one cert: its AKI equals the intermediate's SKI, identical in both certs. That's why either path builds.
→ Encode the issuer from the issuer cert's exact bytes, not a re-parsed string — OpenSSL does strict DN matching and rejects a mismatch even when the signature is valid.
→ The private key stays in the HSM, non-exportable, throughout.


Cross-signing is invisible when it works, and very visible when it's missing. Understand it before you need it.
